# JobMaxxing

[Open the live guest demo](https://jobmaxxing-linda.onrender.com/)

The intended outcome is that a student can have a short career conversation, find several potentially relevant openings, and see where each listing came from and when it was checked. This is a small public-employer-feed prototype, not a complete Handshake replacement.

Run `python3 server.py` from this directory and open `http://127.0.0.1:8765/`.

## Public class demo

The `render.yaml` Blueprint runs a guest-only version on Render. It has current public job feeds, guided career chat, browser-only saved jobs, and keyword-based resume suggestions. It does **not** offer live AI or online accounts. PDF, DOCX, and TXT resumes are briefly read in server memory for keyword matching; the files are not saved. The public demo does not load the local `.env`, account database, or Ollama model. The local version below retains its AI and account features.

The public demo is deployed at [jobmaxxing-linda.onrender.com](https://jobmaxxing-linda.onrender.com/). Render's free service can take about a minute to wake after inactivity. In a fresh browser, complete or skip the guide, chat, browse jobs, save one, and upload a non-personal test resume. Do not use a GitHub Pages URL for the app: Pages cannot run its Python API.

The first visit in a browser opens a four-step guide that points to the career chat bubble, resume drop zone, job search and filters, and Saved jobs. The guide moves to the relevant screen for each step, then returns visitors to their original screen and scroll position when they finish, skip, or press Escape. **Skip** is available at every step. Finishing or skipping is remembered in that browser; **How it works** in the header opens the guide again.

Before the conversation begins, students choose **I have a direction** or **I'm still exploring**. The choice and a welcoming first question then appear as the opening messages in chat history. Students can change paths later without losing earlier messages. Guest history stays in this browser and signed-in history stays with the account; guest choices also follow a later sign-up. When AI is unavailable, the exploring path is a guided preview rather than a model-generated assessment. Browsing jobs is available from either path at any time.

The app opens directly into the career conversation, but no longer requires three answers before jobs can be viewed. The **Browse jobs / Back to jobs** action in the conversation header is always available. After any chat message, all currently matching jobs appear in a scrollable panel while the AI reply is still loading; a button below the composer opens those conversation matches in the full job list. A vague answer may get one short follow-up, but the jobs remain available. If no current postings match the stated role and location, the chat says so instead of presenting unrelated roles as matches, and the browse button opens the full list. **Show all jobs** clears the conversation filter. On Discover, Saved, and Profile, **Chat with AI** is in the desktop left navigation, and a floating AI chat bubble stays in the bottom-right above the mobile navigation. Either opens a compact, non-modal conversation over the current page. The popup and full chat share the same history, AI request, thinking/error state, and job matching; the popup previews up to three current listings and can open the filtered job list or the full conversation. Escape or × closes it. It says **Chat with AI** when either the local model or OpenAI is available; otherwise it says **Career chat** and labels the conversation a guided preview. An account is optional: guests can chat, edit their direction, and save jobs in this browser without registering. The first save offers a choice between saving on this device and signing in or creating an account. Guest data uses browser `localStorage`; it does not sync across devices and can be lost if site data is cleared. A later sign-in copies guest preferences and saved jobs into the account, filling only blank account profile fields and leaving an existing account conversation intact. The browser copy remains available after sign-out.

For signed-in users, accounts, conversation history, preferences, and saved job IDs are kept in a local SQLite database at `data/app.sqlite3`. The `data/` directory is ignored by Git. Passwords are hashed with scrypt; session tokens are stored only as hashes and sent to the browser in HttpOnly, SameSite cookies. This is a local prototype, not a production authentication service; public deployment still needs HTTPS, account recovery, rate limiting, and operational security review.

After creating an account or signing in, the app opens **My profile** instead of the guest's basic **My direction** form. The account page summarizes the four career fields, recent chat activity, patterns in saved jobs (when those postings have usable details), and a shortlist from current public listings. It suggests one next action and keeps the editable direction form below the analysis. An empty account shows clear setup prompts instead of invented insights. These leads are starting points, not eligibility or hiring predictions; the account and its saved data live on this Mac's server, not in a cloud sync service.

**Your Direction** now supports broader job exploration. Users can select activities they enjoy (building, design, research, analysis, helping, growth, and operations), add role, skill, and priority details, and set job type, school year, preferred workplace, location strictness, and a minimum USD pay target. A live shortlist updates before saving; **Explore all matches** carries the current choices into Discover, while **Show all jobs** clears that shortlist. Account preferences are stored separately from AI-chat fields, survive sign-in and chat updates, and guest preferences move into a new account. Matches explain which title, preview, or constraint contributed. Priorities affect matching only when they are actually mentioned in the posting preview. A preferred location can be soft or strict. Known conflicts for selected job type, class year, work setup, strict location, and published pay are excluded; missing pay, work setup, or student-year details remain visible with an explicit warning. Older posting dates are ranked lower and flagged. These rules use the feed's limited text and are not an AI judgment, a complete description, an eligibility decision, or a guarantee the employer is still accepting applications.

On this Mac, the ignored `data/` directory contains Ollama and a Qwen 2.5 3B model. Running `python3 server.py` starts the local model if needed. After the initial download, AI chat works without a key or internet connection; it runs on `127.0.0.1` and does not send student messages to OpenAI. The first reply can be slower while the model loads. The site reports `ai_provider: "local"` when ready. The model can make mistakes, so students can correct their direction in the profile form. Profile-based suggestions still use keyword matching in this mode; an uploaded resume can be matched with the local model.

The career conversation has a drop zone for PDF, DOCX, and TXT resumes up to 5 MB. Matching begins automatically after selection or drop. Resume text is extracted in memory, sent only to the local Ollama service on this Mac, and is not sent to OpenAI, saved to an account, browser storage, a database, logs, or a recommendation cache. PDF text extraction uses the built-in macOS PDFKit; scanned PDFs without selectable text are not supported. DOCX and UTF-8 TXT are parsed with the Python standard library. The **Remove** action clears the current resume and its in-session suggestions. Local AI extracts role and skill signals grounded in the resume; the app then ranks only current job-feed listings against those signals and returns brief explanations. An explicit job-seeking sentence can constrain results to a stated internship, remote setup, city or US location, and a clearly named role such as product design or software engineering. If no current listing fits those constraints, the app reports no matches instead of relaxing them silently. Vague resumes remain broad. It omits listings whose titles explicitly identify them as PhD, doctoral, or postdoctoral roles. When the resume explicitly identifies the applicant as a student, it also leaves out clearly senior-level non-internship titles and high-school internships, while favoring early-career and internship roles. Other eligibility still needs to be checked on the employer posting. The model cannot invent job IDs. Scores are relevance estimates, not admission or eligibility odds.

OpenAI remains optional for AI-ranked job suggestions. Put your own `OPENAI_API_KEY` in the local `.env` file (copy `.env.example` if missing), then restart the server. `.env` is ignored by Git and read only by the server; never put a key in browser JavaScript. `OPENAI_MODEL` optionally overrides the default `gpt-4o-mini`. When present, OpenAI takes precedence over the local model. A configured key still needs valid API access.

With OpenAI configured, the AI conversation updates four editable career fields. The server then selects up to 48 current public listings for AI review, sends only the career fields and those listings' public titles, locations, types, teams, and short summaries, and receives up to eight ranked suggestions with brief reasons. It accepts only IDs from the current feed, so the model cannot create a job listing. Chat history is sent for conversation, but not for job ranking. Both calls use the OpenAI Responses API with `store: false` and [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs). Resume matching is separate and always local, even when OpenAI is configured. These are suggestions, not eligibility decisions; the original posting remains the source of truth. Without a key, the app says **keyword suggestions** and uses local matching, including common student terms such as computer science, internships, and remote work.

Job discovery searches 13 public employer boards across Greenhouse, Lever, and Ashby: Figma, Duolingo, Reddit, Asana, Databricks, Roblox, Khan Academy, Coursera, Stripe, Dropbox, Twilio, Palantir, and Linear. It also includes remote listings from Remotive's public API, labeled **Remotive** and linked back to Remotive as required by its API terms. These are not Handshake or LinkedIn listings. Links below the list open current searches on LinkedIn (using the entered keywords, location, and job type; restricted to the past week) and Handshake (where a school sign-in may be needed). Neither site has been represented as an imported feed. A single scrolling list puts title-based suggestions informed by the conversation first, followed by the remaining public jobs, without switching between tabs. It initially shows 50 matching jobs, then adds 50 at a time; Saved jobs remain paged by 20. Visible job-type categories above the list show counts for internships, full-time and part-time work; fellowship, contract, and other/unlisted types remain available when present. Selecting Internships reveals freshman, sophomore, junior, and senior choices. Only explicit undergraduate-year wording from posting descriptions is treated as a stated year; other internships remain visible as **year not stated**, while jobs explicitly naming different years are excluded. Clearly high-school or advanced-degree internship titles are excluded from undergraduate-year views. Counts reflect the current search and other filters, and class-year counts mean explicit mentions—not all potentially eligible openings. When requested, explicitly labeled internships or early-career jobs are favored among suggestions; broader openings stay in the list. Search includes titles, employers, departments, types, and locations. Filters cover job type (where provided), location, workplace, clearly labeled early-career roles, and sort order. The separate early-career filter is **off by default** so it does not silently hide broader jobs.

The server checks employer sources in parallel and caches results for 15 minutes; Refresh rechecks them immediately. Remotive recommends at most four API requests per day, so its response is cached for six hours, including across server restarts in `data/remotive-cache.json`. Refresh reuses that response until the six hours pass. Remotive says its public API listings are delayed by 24 hours, so this source is additional coverage rather than an instant posting alert. A single failed source does not hide healthy sources. Its prior results may remain for up to an hour, marked cached; after that it is marked unavailable. If every source is unavailable and no valid cache remains, the app shows an explicit error rather than invented listings. Each list row clearly labels location and team, shows employment type and work setup, source and posted date, and gives a short role preview plus any eligibility detail found in the posting. Company introductions are skipped where possible. If the feed does not include substantive role or eligibility details, the row says so and points the student to the employer posting. AI suggestions appear as a separate tag rather than replacing job information. Expanding an employer row loads the full employer description on demand; Remotive descriptions and published pay come from its cached feed. The workspace shows the last check time plus source health. A posted date is not the same as the last verification time. Openings can close between checks, so applicants should confirm on the original posting.

Saved jobs now retain a small local snapshot. If a saved listing is absent from the current feed, it remains visible with a clear **not currently verified** warning. Existing saved IDs migrate without data loss; older saved entries without a snapshot may not be displayable until found again.

## Repeatable matching check

From this directory, run `node --test test_direction_matcher.js`. It uses sample job postings to check that chosen job type, school year, location, workplace, and pay affect the shortlist; unknown details are called out; and unrelated recruiter/senior roles do not slip in from broad keywords. This caught a false match where “programming” in a senior event-marketing title looked like a software job, and a broad HCI-to-design interpretation. The check can confirm our matching rules, but it cannot verify that a real employer feed is complete, a posting remains open, or that a person meets an employer's requirements. The server integration suite also checks that preferences persist across chat, guest import, and login: `python3 -m unittest -q test_server.py`.

This design takes inspiration from [Handshake's official student search guidance](https://support.joinhandshake.com/hc/en-us/articles/218693408-Searching-for-Jobs-and-Internships): profile-informed discovery, keyword and employer search, filters, sorting, and saved roles. Handshake's school-targeted inventory, alerts, qualifications, and application system are not integrated here. Neither a Handshake login nor scraping of private listings is used.

Optional environment variables: `PORT` for the port and `JOBMAXXING_DB` for an alternate local SQLite path (useful for tests). `RESUMEMAXXING_DB` remains a compatibility alias. `JOBMAXXING_PUBLIC_DEMO=1` switches to the guest-only hosted mode and binds to the hosting platform's port; never use the local account mode on a public host.
